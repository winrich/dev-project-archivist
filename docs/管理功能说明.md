# 管理功能设计说明

## 需求与边界

用户需要在界面上登录，然后维护「已纳入监测的项目列表」：改名、取消关注、置顶、查看详情。追加需求：端口可调整；改名只改显示名，目录名另设独立入口。

明确不做：多账号与角色权限、远程访问、云端同步、永久删除（v1 只做软删除）。

## 架构

```
manage_web.html  ←浏览器→  manage_ui.py（HTTP + 登录 + CSRF）
                                  │
                                  ▼
                           manage_store.py（数据层）
                                  │
                    overrides.json / state.json / INDEX.md
                                  │
                           archiver.py（原有流水线）
```

- 人工配置以**工作区路径**为键写 `overrides.json`，不用目录名。改名后配置不失联。
- 所有写操作持有 `Lock(target)` 与进程内串行锁，与每日定时任务互斥。
- 索引是**完整账本**：取消关注只在列表与 `find` 中隐藏，不删条目。

## 字段语义

| 字段 | 写入位置 | 作用 |
|---|---|---|
| `title` | overrides.json | 显示名；README 与索引优先取它；目录名不变 |
| `watching=false` | overrides.json | 取消关注；列表/`find` 隐藏，「全部」可见 |
| `pinned=true` | overrides.json | 索引与管理列表置顶 |
| `note` | overrides.json | 人工备注，仅管理台展示 |
| `skip=true` | overrides.json | 停止归档（删除操作设置） |

## 改名与目录改名分离

- `rename()`：写 `title` + `state.name`，设 `name_source="manual"`。`render` 见到 manual 就不再按 LLM 摘要改名。
- `rename_dir()`：只做 `os.rename`，改 `state.dir`。显示名不受影响。
- 两者均先备份 `state.json`/`overrides.json`/`index.json`/`INDEX.md` 到 `_trash/_manage_backups/`，失败整体回滚。
- 目录名做严格校验（禁止 `\/:*?"<>|`、`.`、`..`），不调用 `safe_name` 悄悄替换——避免 `a/b` 变成 `a b` 这种意外路径。

## 认证

- 口令首次随机生成（16 字符）只打印一次；环境变量 `ARCHIVER_MANAGE_PASSWORD` 可覆盖。
- 存储 salt + PBKDF2-SHA256（20 万轮）哈希，明文不落盘。
- 会话 Cookie：HttpOnly + SameSite=Strict + 8 小时过期；CSRF token 只在登录响应体返回，写操作校验 `X-CSRF-Token`。
- 连续 5 次口令失败锁定 60 秒。仅绑 `127.0.0.1`。
- 设置页支持**在线改口令**（`POST /api/password`）：校验原口令 + CSRF + 新口令≥6 字符，重写 salt+hash 并更新进程内配置，明文不落盘。改口令后需用新口令重新登录。这解决了「服务重启（未带环境变量）生成新随机口令、旧口令失效」的问题。

## 多视图管理台（树形导航）

前端仍是单文件零外链，改为左侧树形导航 + 右侧内容区，视图间切换不刷新页面。

| 分组 | 视图 | 数据来源 | 说明 |
|---|---|---|---|
| 总览 | 数据概览 | `overview()` | 项目/关注/归档/文件/体积统计，类型·活跃度·语言分布，近 14 天活动量，最近更新项目 |
| 管理 | 项目管理 | `projects()` | 原列表；新增类型/语言/日期筛选、每页 10/20/50/全部、翻页、活跃度列与迷你图 |
| 分析 | 活跃度排行 | `ranking()` | 关注中项目按活跃度降序，同分按最近开发时间 |
| 分析 | 按日期报告 | `report_data()` + `reports.db` (SQLite) | 上半区：历史报告按日期检索 + iframe 看原报告；下半区：现场生成实时概览 |
| 系统 | 设置 | — | 改口令、每页数量首选项（存 localStorage） |

接口（均需登录）：`GET /api/overview`、`GET /api/ranking`、`GET /api/report?days&end`（现场生成）、`GET /api/reports?offset&limit`（档案列表）、`GET /api/report-archive?date=YYYY-MM-DD`（按日检索）、`GET /report/<name>`（认证后 serve 归档 HTML）；写接口 `POST /api/password`。

**注意**：报告页数据来自**原始对话数据源**（`collect_range`），与项目管理页的归档视角口径不同，页面已标注。

## 报告档案库（SQLite）

把「每天生成的报告」沉淀成可检索的档案，解决原报告页只算不存、无法回看历史的问题。为承接多平台、大数据量，存储从 JSON 迁到 **SQLite**（`report_store.py`，Python 标准库 `sqlite3`，零第三方依赖）。

**表结构**（`reports.db`，归档根目录）：

| 表 | 主键 | 主要字段 | 索引 |
|---|---|---|---|
| `reports` | `name` | `source, date_from, date_to, days, generated_at, prompts, sessions, projects, files, tokens, sha256, bytes` | `date_to DESC`、`source+date_to` |
| `sessions` | `sid` | `source, workspace, title, created, updated, status` | `source+created`、`workspace` |
| `meta` | `key` | `value`（schema_version / updated_at） | — |

- `source` 字段区分多平台（workbuddy / claude_code / codebuddy…），`sessions` 表按平台承接会话明细——这是大数据量下 JSON 全量读写的真正瓶颈所在，SQL 按索引查询是 O(log n)。
- **只存元信息**，HTML 正文与转录仍在文件系统，DB 损坏不毁原始资料。

**读写**：
- **写入**：`report` 命令落盘 HTML 后**双写**——SQLite 为主 + `report_index.json` 镜像（回退源保留，不删）。每天一份近 30 天滚动报告，文件名 `report-{from}_{to}.html` 不覆盖；主键 UPSERT 幂等。
- **读取**：`manage_store.report_list()/report_archive()` 走 SQL，接口签名不变（前端零改动）；DB 不可用时自动回退读 JSON。分页、按日期范围全下推到 SQL。
- **检索语义**：`date_from <= date <= date_to` 命中（滚动报告互相重叠），附 `day_index`（该日是区间内第几天）。
- **详情**：日期检索或列出全部 → 点「查看」→ iframe 内嵌 `/report/<name>` 原样展示那份完整 HTML。

**会话明细**：`sessions-sync` 子命令从各平台转录（`build_index()`）全量刷新 `sessions` 表（事务内替换，幂等）。当前 246 条会话。

**迁移命令**：
- `report-migrate`：把旧 `report_index.json` 导入 SQLite + 抽取会话明细，幂等，旧 JSON 保留。
- `report-backfill`：把 `report/` 下已有 HTML 补登进 JSON 索引（早在 JSON 时代的功能，双写下仍可用）。

**每日自动生成**：夜间 02:30 归档任务第 4 步运行 `report --days 30`，自动双写登记；无需人工干预。

## 空壳项目的对话入口修复

**现象**：空壳项目（工作区里没有源码文件）详情看不到"打开原对话"，即使原始对话确实存在。典型如「编写GitHub访问自动化维护工具」——对话有 3397 行、1078 次工具调用，成果在工作区外的 `D:/Projects/JoyBang/...`，但工作区本身只有 `.workbuddy`。

**根因链**：
1. `Project.compute()` 只扫 `workspace` 目录；工作区 0 源码 → `total_files=0` → 判"空壳"。
2. render 只对"代码项目/混合产物"建归档目录；空壳只在 state 留一行、`dir` 为空、**从不写 `_meta/conversations.md`**。
3. `detail()` 原本只读归档目录的 conversations.md → 空壳项目对话列表为空。

**修复**：`detail()` 在无 conversations.md 时，从 SQLite `sessions` 表按工作区路径查原始会话，用 `deep_link_of()` 生成 `workbuddy://chat/<sid>` 深链兜底。已验证该 GitHub 项目详情恢复 1 条带深链的对话。

**边界**：这修的是**对话入口**。工作区外的源码成果（`D:/Projects/JoyBang/...`）仍不在归档范围内——归档器按设计只归档工作区内文件。若要把外部仓库纳入，属于改变归档边界的另一话题，未在本轮做。

## 活跃度量化算法

单个项目活跃度分数 `A∈[0,100]`，四维加权（参数集中在 `manage_store.py` 顶部常量）：

| 维度 | 权重 | 公式 | 含义 |
|---|---|---|---|
| 近期性 R | 40% | `100 × 0.5^(距今天数/30)` | 30 天半衰期：今天 100，30 天前 50，90 天前 ~12 |
| 频次 F | 30% | `min(100, 25×log₂(1+会话数))` | 1 次=25，7 次=75，15 次封顶 |
| 产出 O | 20% | `min(100, 12×log₂(1+文件数))` | 46 文件≈67 |
| 持续度 C | 10% | `min(100, 活跃天数/10×100)` | 会话明细里的不同日期数，10 天满分 |

- `A = round(0.4R + 0.3F + 0.2O + 0.1C)`；分档：🔥≥70 高热 / 🟢45–69 活跃 / 🟡20–44 平稳 / ⚪<20 沉寂。
- **迷你图**：近 14 天每日会话数，从 `_meta/conversations.md` 的「时间」字段按天聚合。
- **降级**：无会话明细时 C=0、迷你图全零，R/F/O 照常；`today` 可注入便于单测。
- 设计取舍：以近期性为主避免历史大项目长期霸榜；对数压缩让高频文档任务与代码项目可比。权重/半衰期集中在常量，便于调参。

## 踩坑记录

1. **LLM 摘要会覆盖人工改名**：`render` 里 `st.name != s.title` 就重命名目录。必须加 `name_source != "manual"` 守卫，否则人工改名下次 `run` 就被改回去。
2. **`safe_name` 不是校验器**：它把非法字符替换为空格。目录名入口必须自己用正则严格拒绝，否则 `a/b` 会静默变成 `a b`。
3. **`skip=true` 不会清理旧目录**：原代码只在扫描时跳过，不动已归档目录。删除操作要显式调用 `trash_project()`。
4. **index.json 结构不能随便加字段**：无管理字段时必须保持原样，否则既有测试与幂等性被破坏。做法是先生成原结构，再按显式字段追加。
5. **测试里不能硬编码家目录**：仓库有 `test_public_content` 扫描真实用户名路径，测试文件也要用 `__file__` 推导路径。
6. **测试目录改名时显示名来自 `_summary.json`**：断言「显示名不变」要记录操作前的值，不能假设等于 `state.name`。
7. **活跃度日期单位**：`state.json` 的 `last_ts` 是**毫秒**，`conversations.md` 的时间是 ISO 字符串（`YYYY-MM-DD HH:MM`）。两者混用会算错近期性——`A.day()` 已自动识别毫秒，聚合会话时取 ISO 前 10 位。
8. **改口令接口必须先过 CSRF**：写操作校验顺序是「认证 → CSRF → 业务」。测试口令错误/过短时必须带 csrf，否则先被 403 拦截，测不到业务分支。
9. **重启会重置随机口令**：只要没带 `ARCHIVER_MANAGE_PASSWORD`，每次启动都生成新随机口令并覆盖哈希，跨会话旧口令必失效。要么始终带环境变量启动，要么在设置页改成固定口令。
10. **serve 归档 HTML 必须白名单**：报告文件名只能匹配 `report-YYYY-MM-DD_YYYY-MM-DD.html`。若直接拼接 `target/report/<name>` 而不校验，`/report/../../state.json` 会读到 state.json（登录后可穿透）。管理台是本地服务也不可省这一步。
11. **索引写入要持同一把锁**：`cmd_report` 登记索引与夜间任务写 state 可能并发，索引读-改-写必须包在 `A.Lock(target)` 内，否则会丢条目。HTML 落盘本身不改归档正文，无需持锁。
12. **存量报告的摘要无法反推**：HTML 是渲染后的成品，`report-backfill` 只能从文件名取区间、`stat` 取生成时间；prompts/tokens 等摘要字段只能留 0。不要试图正则解析 HTML 里的数字——格式一变就错，且得不偿失。
13. **SQLite 用短连接 + WAL**：每次操作开→关连接，配合 `PRAGMA journal_mode=WAL` 与 `busy_timeout=30000`，管理台与夜间任务可并发读写；写事务用 `BEGIN IMMEDIATE` 防两个写者。不要用长连接（多进程下会锁死）。
14. **数据层切 SQL 后旧测试的写法要跟着改**：`test_report_archive.py` 早期用 `index_report()` 只写 JSON 索引，切到 SQLite 后 `ManageStore` 读到的是空库（不会回退，因为 `init_schema` 成功）——测试必须改用 `ReportDB.upsert_report()` 写数据。这是"回退源不等于测试源"的典型坑。
15. **测试数据里不能写真实家目录**：`test_public_content` 会扫描全仓库文本，`C:/Users/henry` 这类会触发防泄漏失败。测试里一律用 `C:/Users/name/...` 等虚构占位名（`ALLOWED_HOME` 白名单内的名字）。
