## 0. 修正：缺口不在"怎么触发"，在"产出值不值得看"

| 我之前的判断           | 实际情况                                                                     | 结论                            |
| ---------------- | ------------------------------------------------------------------------ | ----------------------------- |
| ❌ 触发靠"记得跑"，缺环境钩子 | 已有每日定时任务（`references/automation-prompt.md`：scan → pending → 归纳 → render） | **该项作废**，不设 `hook` 命令         |
| ❌ 产物不在视线内、无版本    | `git_init()` 在每次 scan/render 末尾自动提交，每项目独立仓库                              | **部分作废**：git 已有，"自动批量提交"只是加强项 |

于是真正的三个缺口变成：

| # | 缺口              | 证据                                                                                                   |
| - | --------------- | ---------------------------------------------------------------------------------------------------- |
| 1 | **账本在记，但记的是废话** | 所有提交信息都是 `sync: 同步 X 归档内容` / `init: 归档 X`（`archiver.py:1480`、`1495`），`git log` 27 个仓库全是同一行，看不出哪天做了什么 |
| 2 | **没有入口**        | 没有 `find`。27 个项目，找东西得先打开 `INDEX.md` 再猜                                                               |
| 3 | **没有账本视图**      | `daylog` 只能看单天，`log` 只出单天文件，跨天/跨项目/跨工具的汇总不存在                                                         |

第 1 条是这次新增的判断，也是**性价比最高的一个**：它把"每日定时 + git 产物"这两个已经成立的设计真正兑现掉。

## 1. 核心架构决定：一个聚合，三个视图

现在 `collect_day(date_str)` 已经存在且被 `run_daylog` / `cmd_log` 共用。往下所有新命令都**不应该各写一套聚合**，否则口径必然漂移（这是上一轮踩过的坑：预览和落盘对不上）。

```
                    ┌───────────────────────────────┐
   转录 → 归一事件 → │ collect_range(since, until)   │ ← 由 collect_day 泛化
                    └───────────────┬───────────────┘
                                    │
        ┌───────────────┬───────────┴────────┬──────────────┐
     daylog(单天)     stats(周/月)       commit-msg      report(HTML)
```

- `collect_day(d)` 改成 `collect_range(d, d)` 的薄封装，行为不变、测试继续绿。
- `stats` / `report` / 提交信息生成器全部消费 `collect_range` 的同一份结构。
- **不引入任何新的中间存储**。

### 2.3 提交信息生成器 —— 把 git log 变成账本

**解决**：27 个仓库、每天一条 `sync: 同步 X 归档内容`。账本记了，但记的是"今天有变化"。

**改哪里**：`git_init()` 增加可选参数 `message`，由调用方（`run_scan`/`run_render`）在提交前用 `collect_range(today, today)` 里**该工作区**的 turns 生成。

格式（确定性，无 LLM，脱敏后写入）：

```
2026-11-18 · 3 指令 · 12 文件

- 08:12 把 HighQualityCrop 的插值换成 LANCZOS4 后重跑
- 21:36 给 daylog 加数据完整性体检
- 23:10 检查 igdfcl32 崩溃的调用栈
```

规则：

| 项   | 规则                                               |
| --- | ------------------------------------------------ |
| 标题行 | `YYYY-MM-DD · N 指令 · M 文件`                       |
| 明细  | 最多 5 条，倒序，每条截断 40 字，去换行                          |
| 脱敏  | 复用 `desensitize()` + `safe_path_label()`，敏感路径不出现 |
| 兜底  | 当天无 turns（如仅 render 变化）→ 保留原 `sync:` 文案，不编造      |
| 幂等  | 内容未变仍不提交（现有 `git status --porcelain` 判空逻辑不动）     |
| 首次  | `init: 归档 <name>` 保持不变                           |

**附带收益（这是 star 卖点级的能力）**：每天一提交 = 逐日快照，`git log` 本身就是时间轴。配合 3.3 的 `restore`，就成了"能回滚到上周三的代码"。

**验收**：连跑两天（或用 `--date` 指定两天）后，`git -C <项目> log --oneline -5` 能看到带日期的可读条目；连跑两次同一天，第二次无新提交（幂等）；日志里无敏感路径。

### 3.2 `report`（单文件 HTML）

同一份数据，供截图传播。卡片墙 + 一年热力图 + token 曲线 + 页脚仓库链接。零依赖、双击打开、可离线。**这是"个人归档看板"，不是被否掉的"领导看板"** ——区别是数据属于自己（炫耀素材）还是属于员工（监控工具）。

### 3.3 `restore --date`（时间机器）· ✅ 已实现（0.3.0 第六项）

```bash
$ archiver.py restore --date 2026-11-10                    # 预览，零写入
$ archiver.py restore --date 2026-11-10 --write            # → <target>/_restore/2026-11-10/
$ archiver.py restore --date 2026-11-10 --write --only LedgerSync
```

安全约束（硬性）：

- **只写新目录**，默认 `<target>/_restore/<date>/<项目>/`，绝不覆盖既有目录；
- 目标目录非空 → 拒绝，除非 `--force`；单次总量 > 800MB 也要 `--force`；
- 归档目录本身只读（`git archive`，不碰工作区与索引）；
- 仓库无该日期之前的提交 → 归入"无法恢复"并写明**首次归档日期**（比"无历史"更有用）。

**落地时改掉的两处设计**：

| 计划里写的 | 实际做成 | 理由 |
|---|---|---|
| `restore <项目>` 位置参数 + `--to 目录` | `--only 关键字` + `--out 目录` | 与既有 `scan --only`、`log/report --out` 一致，不新增第二套词；顺带支持"全量恢复再过滤" |
| 默认直接写 `./restore-<项目>-<日期>` | 默认**只预览**，`--write` 才落盘 | 一次可能几百 MB，先看清取到哪一版、多少文件再决定 |

**语义口径（写进了 README / SKILL / 代码注释三处）**：只能回到"那天确实归档过"的快照；
某天没跑归档就退到更早的最近一次提交并打出它的真实时间；从来没归档过的文件（媒体、超大二进制、
敏感路径、首次归档之前）不在快照里——**它是时间机器，不是备份**。

**为什么值得做**：这是"归档"变"账本"最硬的实用价值——**你以为丢了的代码，能回到上周三的样子**。而且能力已经存在，只差一行命令。

## 8. 一个要提前想清楚的风险

**每日提交会让归档仓库长期膨胀。** 现在只有 `git-clean` 手动兜底，且首次 `init` 后跑过 `gc --prune=now`，之后不再 gc。

建议在 `status` 里加一行体积体检：某个仓库 `.git` 超过 200MB 时提示"建议 `git gc`"。别做自动 gc——它会在每日定时任务里拖长执行时间，得不偿失。
