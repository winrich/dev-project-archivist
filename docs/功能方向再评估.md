# dev-project-archivist · 功能方向再评估

> 2026-11-18 重做。上一版《增长路线图》讲的是"补齐工程底座"，那一批已经完成（CI、49 个测试、跨平台脚本、pyproject、`daylog`/`log`）。
> 这一版换一个问题：**代码已经够扎实了，为什么还是不会有人 star？**

---

## 0. 一句话结论

**这个项目现在把"基础设施"当"产品"在卖。**

`scan` / `render` 是一个每月跑一次的体力活，而它被放在了 README 的第一屏、被当成了产品本体。
真正每天会被打开的东西——"我上次那个脚本在哪""这周我到底在忙什么"——一个都还没有。

---

## 1. 用对标产品的曲线反推差距

对标产品 跑到 210K 安装，不是因为它的功能多。它的路径是三个"零决策"：

| 环节 | 对标产品 | 本项目 | 差在哪 |
|---|---|---|---|
| 装 | 扩展市场一键装 | clone 到 skills 目录 | 摩擦高一个量级 |
| 触发 | 每次对话自动存 | 要记得跑 `run` | **依赖人的记忆 = 最大的流失点** |
| 首次价值 | 当次对话就落成 `.md` | 要有几个月历史才好看 | 新用户冷启动为 0 |
| 产物位置 | 在仓库里，`git status` 就能看见 | 在 `~/Workbuddy项目归档`，看不见 | 不在视线内 |
| 传播 | 可分享的会话链接 | 无 | 无裂变 |

### 更要紧的一个错位

再看本项目各命令的**真实使用频率**：

| 命令 | 合理频率 | 现在的位置 |
|---|---|---|
| `scan` / `render` / `run` | 每月一次 | **README 首屏主角** |
| `find`（不存在） | 每天 | 缺失 |
| `stats`（不存在） | 每周 | 缺失 |
| `daylog` / `log` | 每天 | 藏在文档第 330 行 |

**最常用的入口不存在，最不常用的被摆在门口。** 这就是 0 star 的产品侧原因——不是没人看见，是看见的人试完发现"这东西跟我明天没关系"。

## 2. 试用人第一眼看到什么（实测）

刚跑了一次 `scan --dry-run`，本机真实数据：

```text
[1/5] 会话索引：25 个会话，25 份转录
[2/5] 归并完成：23 个项目单元

2026-03-28  空壳      —              0  0    0  Claw  Claw
2026-06-26  空壳      —              0  0    0  https  2026-06-26-21-39-43

2026-10-01  空壳      —              0  0    0  密码为什么为空 InternetGatewa  2026-10-01
...
小计：代码项目 8 / 文档任务 4 / 其余 11
```

**23 行里 11 行是空壳或混合产物，占 48%。项目名有叫 `https` 的、有叫"密码为什么为空"的。**

这是可发现性的**前置条件**，比推广重要得多：

- README 首屏写着"27 个项目"，试用人跑出来一半是 `https`，**第一反应是"这工具不准"**，不是"我数据不干净"。
- 他不会再跑第二次，也不会 star，更不会去读你 430 行的文档。

### 根因在代码里，很清楚

`archiver.py:807 _guess_name()` 的命名来源只有三个：会话标题 → 语言 → 工作区目录名。
**它从来不读磁盘上的身份证据**：

```python
def _guess_name(self):
    """预命名：优先取最像项目名的会话标题，其次取语言/目录名"""
    titles = [...]
    t = pick_title([x for x in titles if x])
    if t: return safe_name(t)          # ← "https"、"密码为什么为空" 都是这么来的
```

真实项目在磁盘上是有身份证的：`git remote origin` 的仓库名、`package.json` 的 `name`、`*.csproj` 的 `AssemblyName`、`*.sln` 文件名、`pyproject.toml` 的 `name`。这些一个都没用。

**会话标题是"用户随口说的话"，不是"项目叫什么"。拿前者当后者，是这个工具最贵的一个设计失误。**

## 3. 功能方向：三个钩子，一个闭环

star 和日活都来自三个钩子之一。缺一个还能活，缺三个就是现在这样。

| 钩子 | 心理机制 | 对应功能 | 当前状态 |
|---|---|---|---|
| **A 洞察钩子** | "它告诉了一件关于我自己的、我之前不知道的事" | `stats` | 无 |
| **B 环境钩子** | "它已经跑过了，我不用记" | `hook` + `NOW.md` | 无 |
| **C 分享钩子** | "这个图我能发出去" | `report` → 单文件 HTML | 无 |
| **闭环** | "我要找的东西 3 秒就出来了" | `find` | 无 |

### A. `stats` —— 把 Faros 卖钱的东西做成个人版

这是我认为**star 弹性最大**的一个，理由有三：

1. **第一天就有数据**。新用户哪怕只有今天的会话，`stats --today` 也能出东西，彻底解决冷启动。
2. **它是"关于我自己"的**。人对自己花了多少钱、多少 token 有天然好奇，这是唯一能让人主动截图的动力。
3. **别人做不了**。跨 Claude Code + WorkBuddy + Cursor 出总表，需要"多适配器 + 归一事件"这套底座——你恰好已经有了。国内没有等价品，海外 Faros / Jellyfish 只卖企业。

数据可行性已实测确认：

| 需要 | 有没有 | 证据 |
|---|---|---|
| token 三分量 | 有 | `usage` 事件 `in/out/cache_read` |
| 按项目聚合 | 有 | `collect_day()` 已按工作区聚合 |
| 按天/周区间 | 有 | `DayCollector` 游标分桶 |
| 模型归属 | **部分** | WorkBuddy 写 `providerData.requestModelName`（常为 `auto`）；Claude Code 写 `message.model` |

输出形态（一屏，可截图）：

```text
近 7 天 · 3 个项目 · 2 个 AI 工具

项目                      天数  指令   写   token    全价部分   缓存命中
BatchRenamer                  4    38   61   28.4M     0.31M       99%
InvoiceParser          2    19   44   19.2M     0.42M       98%
dev-project-archivist       2    33   27   11.1M     0.18M       98%

合计          输入 58.72M · 输出 0.83M · 缓存命中 57.9M（98.6%）
              全价部分 0.91M  ← 这才是真花钱的部分
模型归属      未记录 60%（WorkBuddy 报 auto）  ← 不拿默认价顶替
```

**必须守住的原则**：模型不明就写"未记录"，不要用某个默认单价去乘。
这条和你 `daylog` 里"不能拿 0 顶替没数据"是同一个原则——**便宜和没数据在报表里长得一样，是致命的**。

### B. `hook` —— 把它从"我记得跑"变成"它已经跑了"

Claude Code 有 `SessionEnd` / `Stop` hook，WorkBuddy 有自动化。两个平台都支持在会话结束时执行一条命令，而 `log` 恰好**已经幂等**（连跑两次 md5 不变，这个测试是现成的）。

于是可以做到：

```bash
archiver.py log --date today        # 挂在 SessionEnd，跑一百次也只生成一份
```

顺手再加一个 `NOW.md`（我认为这是最被低估的一个功能）：

```markdown
# 当前进行中 · 2026-11-18 23:30

## InvoiceParser
最后一条指令：把 HighQualityCrop 的插值换成 LANCZOS4 后重跑 831 样本
改了：CropService.cs、PhotoPipeline.cs
最后状态：测试跑到 412/831，无报错
下一步线索：还有 419 个样本没跑完（指令里明确说了"先跑 831 全量"）
```

**这是一个"接得上"的文件，不是"日志"。** 第二天早上打开 `NOW.md`，不需要回看任何对话。对标产品 想解决的"下次接不上上下文"，你用确定性数据就能做，而且不用调模型——因为"最后一条指令 + 改了什么 + 最后有没有报错"全在 `turns` 里。

`install-hook` 子命令负责写配置，一个命令搞定，用户不用读文档。

### C. `report` —— 单文件 HTML，为截图而生

`INDEX.md` 是给人读的，`report` 是给**传播**用的。单文件、零依赖、双击打开：

- 项目卡片墙（按最近活跃排序，带语言色块和代码行数）
- GitHub 风格的一年热力图（哪天在几个项目上动过）
- token 曲线（近 90 天）
- 页脚一行：`Generated by dev-project-archivist`

**注意这是"个人归档看板"，不是上一轮否掉的"领导看板"。** 区别在于数据是"我自己的项目"而不是"员工的工时"——前者是炫耀素材，后者是监控工具，社区对这两件事的反应完全相反。

这也顺手把"可视化"这个缺口补上了：现在 README 里一张图都没有，而首屏 10 秒 GIF 是把访客转成试用人最便宜的手段。

### D. `find` —— 从"博物馆"变回"工具"

现在的归档是个博物馆：东西都在，但得先知道在哪一格。真实场景是——

> "上个月我写过一个把批处理转 PowerShell 的小脚本，在哪来着？"

现在的解法：打开 `INDEX.md` → 找到 27 个项目 → 猜是哪个 → 点进去 → 翻 `_meta/conversations.md`。**没人会这么干。**

应该是一条命令：

```bash
$ archiver.py find "批处理 PowerShell"
InvoiceParser  ·  2026-11-12  ·  修复 GitHub 页面布局
  → 21:04  "写个批处理把 build.bat 转成 ps1"            [命中指令]
  → tools/convert.ps1（新增，42 行）                     [命中文件]
  → C:/Users/me/WorkBuddy/2026-11-12-21-04-11        [回场]
  open: archiver.py find "批处理 PowerShell" --open
```

**实现成本极低**：`index.json` 已有项目元数据，每个项目已有 `_meta/conversations.md` 存全部指令原文。`find` 只是"grep + 打分 + 打印"，不需要新建任何存储，约 120–150 行。

但它改变的是**这个工具的使用频率**：从每月一次变成每天。而使用频率决定 star——人只会 star 自己天天用的工具。

## 4. 可信度工程：命名与分类

排在所有新功能之前，因为它是试用转化的**门槛**。

### 4.1 命名按"身份强度"排序

现在的顺序是"会话标题优先"，应该整条反过来：

| 优先级 | 证据 | 强度 | 例 |
|---|---|---|---|
| 1 | 用户手改的名字（`pick_override`，已有） | 最高 | — |
| 2 | `git remote origin` 的仓库名 | 强 | `order-sync` |
| 3 | 清单文件：`package.json` → `*.csproj` → `pyproject.toml` → `*.sln` | 强 | `BatchRenamer` |
| 4 | cwd 目录名（**排除** `2026-11-18-21-34-40` 这种平台自动生成的时间戳目录） | 中 | `MyTools` |
| 5 | 会话标题（现有逻辑） | 弱 | "修复题目导入菜单…" |
| 6 | 语言兜底 | 最弱 | "C# 项目" |

补一条：`is_junk_title()` 现在只挡单字母和图片占位名，应该也挡**纯 URL、纯路径、以"密码为什么为空"这种疑问句开头且长度 > 25 的字符串**。名称超过 20 字基本就不是项目名，是句子。

### 4.2 空壳默认折叠

`--dry-run` 的表里，11 行非项目默认就不该出现。改为：

```text
小计：代码项目 8 / 文档任务 4
另有 11 个会话未构成项目（空壳 7 · 混合产物 4），加 --all 查看
```

一行字，把"48% 是垃圾"变成"你真正有 8 个项目"。**同样的数据，完全不同的观感。**

### 4.3 加 `--explain`

```bash
$ archiver.py scan --dry-run --explain BatchRenamer
BatchRenamer  →  代码项目（置信度 高）
  判定依据：源码 168 个（阈值 5）· 有 .sln 入口 · 4 个会话指向同一工作区
  命名依据：BatchRenamer.csproj 的 AssemblyName（非会话标题）
  收录：168 个文件 / 176 个（排除 8 个：截图 5、构建产物 3）
```

第一次跑的人会怀疑"你判得对不对"。**让他能问"凭什么"，比让判定更准更有效**——因为能被验证的系统才敢信任。

## 5. 明确不做（保持锋利）

| 不做 | 原因 |
|---|---|
| 云端同步 / 账号 | 卖点就是数据不出域，做了等于自毁 |
| 对话问答 / 语义检索 | 对标产品 的正面战场，且它是"管对话"，你是"管产物" |
| SaaS 看板 | 双叙事冲突，开发者社区立刻转向负面 |
| 主流程调 LLM | 确定性是可复现的前提，一旦引入就不可控 |

补一条新的：**不做 Cursor 适配器**（至少现在不做）。
`state.vscdb` 是 SQLite + 私有 schema，版本一升就崩，维护成本无限。等前面四件事做完、有人主动提 Issue 再考虑。**别用一个高维护成本的功能，换来一个"支持 Cursor"的宣传词。**

## 6. 和 对标产品 的关系：说成互补，不要装成竞品

对标产品 存的是**对话**（为什么改），你收的是**产物**（最后留了什么）。这两个是真互补：

- 它的用户在 Issue 里问得最多的一类问题是"能不能把做出来的项目导出"——**这是你的长尾流量入口**。
- README 里加一句明确的互补说明，比在 README 里跟它对比功能更有用（对比会显得你在蹭，互补会显得你懂行）。

推荐措辞：

> 对标产品 帮你留住"为什么"，本项目帮你留住"结果"。两个一起用不冲突。

## 7. 如果只做三件事

按投入产出排序，全部是加法，不动主流程：

| 顺序 | 事项 | 代码量 | 为什么排这个位 |
|---|---|---|---|
| **1** | 命名按身份强度重排 + 空壳默认折叠 | ~80 行 | 决定试用的人会不会留下。**改完之后 `--dry-run` 那张表才配当首屏** |
| **2** | `find` | ~150 行 | 唯一能让使用频率从"每月"变"每天"的功能，零新增存储 |
| **3** | `stats` | ~180 行 | 唯一能让新用户第一天就有价值感、且天然可截图传播的功能 |

三个做完，`v0.2.0` 就有了一个能发出去的标题：

> **不再只是归档：一条命令查回你做过的所有 AI 项目，顺便告诉你这周花了多少 token**

`report`（HTML 看板）和 `hook`（自动落盘）排在第二批。`report` 是传播资产，`hook` 是留存资产——但前提是先有值得传播和值得留存的输出。

## 8. 一个判断，供你否决

**这个项目的长期位置不是"归档器"，是"AI 开发活动的本地账本"。**

归档是账本的一种视图（我做过哪些项目），`daylog` 是另一种（我今天做了什么），`stats` 是第三种（我花了多少）。三者共用同一套"转录 → 归一事件 → 确定性聚合"的底座，而这个底座别人抄起来最费劲——它全是脏活。

如果认同这个位置，README 第一句应该改成：

> 你的 AI 编程工具每天都在产生数据，但没有一个地方能回答：我做过什么、花了多少、东西在哪。
> 这个工具把本机的会话读成一本账，全程离线，零依赖。

归档从"卖点"降级成"功能之一"。这不好受，但**"账本"是每天都有理由打开的东西，"归档"不是。**
