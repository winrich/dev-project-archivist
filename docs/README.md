# 过程文档与样例

这里有两类东西：**判断依据**（写给人回看）和**展示素材**（给 README 用）。

## 一、三份过程记录

不是产品文档。留在这里是为了**将来能回看当时的判断依据**：为什么砍掉某些方向、为什么某个语义要写死、
某个坑当初是怎么踩的。产品文档看根目录的 [README](../README.md) 与 [CHANGELOG](../CHANGELOG.md)。

| 文档 | 回答什么问题 |
|---|---|
| [功能方向再评估](功能方向再评估.md) | 0 star 的真实原因是什么。核心结论：把「基础设施」当「产品」卖——每月跑一次的 `scan`/`render` 占满首屏，天天要用的 `find`/`stats` 根本不存在。 |
| [完善计划](完善计划.md) | 施工单，按 P0 / P1 / P2 / P3 分档，每项写清「为什么值得做」和验收方式。P0 + P1 + P2 已交付（0.3.0、0.4.0）；P3「扩散」受阻，原因与重启条件写在文档里。 |
| [变更说明](变更说明-daylog与仓库改造.md) | 逐项落地记录，十九节。每节含方案对比、踩过的坑（表格）、验证结果、改动文件清单。想知道某个设计为什么长这样，先查这里。 |

## 二、样例素材

| 文件 | 是什么 |
|---|---|
| [sample/build_sample.py](sample/build_sample.py) | 用**虚构数据**调用 `archiver.build_report_html()` 生成样例页。不是手写的仿冒 HTML——渲染器改了，样例跟着变。 |
| [sample/report-demo.html](sample/report-demo.html) | 生成结果：一份 30 天的账本页，双击可看。README 里那张图的来源。 |
| [img/report-demo.png](img/report-demo.png) | 上面那份 HTML 的截图，嵌在 README 首屏。 |

**为什么要有样例**：README 需要一张「这东西长什么样」的图，但真实归档里是使用者自己的项目名、
真实用量和真实时间分布，不能拿来当素材。所以数据全编，渲染走真函数。

改样式或改版式的流程：改 `archiver.py` → 跑 `python docs/sample/build_sample.py` → 重新截图覆盖
`docs/img/report-demo.png`。中间不需要改任何数据代码。

## 与版本号的关系

版本号 = 计划里已完成档位的最高一个，不提前、不落后。阶段名归计划，版本号归产物。
这条规则写在 [CHANGELOG](../CHANGELOG.md) 开头，由 `scripts/tests/test_release.py` 保证三处一致。

因此 `完善计划.md` 里出现的 `v0.2.0` / `v0.3.0` / `v0.4.0` 是**档位编号**，不一定都发布过：
P0 三项 + P1 三项一起交付，首个公开版本是 0.3.0，没有发布过 0.2.0。
